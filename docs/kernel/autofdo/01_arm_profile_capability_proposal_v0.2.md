## 0. 结论先行（相对 v0.1 的变化）

1. **ARM32 内核上的 PMU 采样有两个由硬件决定的失真，这是 v0.1 没有认识到的核心问题。**
   - **IRQ 影子**：PMU 溢出中断是普通 IRQ（GIC，无 NMI）。关中断期间的样本要等到重新开中断才被记录。RPi4 上，落在 IRQ 解除屏蔽指令及其后一条指令的样本占内核样本 35%–60% **[已证实：位置统计]**。TV SoC 的 PMU 同样是普通 SPI 中断 **[已证实]**。
   - **skid**：TV SoC（A53）上，采样点在触发事件之后约 **106 周期**，分布很窄（p99 113 周期），折合 107–212 条指令 **[已证实]**。函数级热度基本可信，块级信息被抹平到上百条指令的范围。
2. **A2（已采纳分支目标采样）关闭。** RPi4 的 A72 不实现所需事件；TV SoC 的 A53 实现了 `PC_WRITE_RETIRED`（0x0C），计数语义已证实为"已采纳分支"，但 skid 远大于基本块长度，采样点不能指出分支目标 **[已证实]**。0x0C 保留为计数类机制指标。
3. **分支与执行次数信息改由插桩计数提供：A4 改为 R2（GCOV 计数 profile）。** 主线 GCOV 内核支持 ARM，无需移植 PGO 运行时。实验室插桩构建跑训练负载，得到行与块的执行次数，转换为 sample profile。它不受影子与 skid 影响，语义上是执行次数，与上游 x86 分支采样 profile 更接近。
4. **创新点重新定位为"ARM32 采样失真的修正与融合"：**
   - **R1 影子修正**：用内核调用栈把影子样本归回调用者；以 R2 为真值评价；
   - **B1 融合（改写）**：现场 IP 样本给"热多少"（函数量级），实验室 GCOV 计数给"怎么走"（函数内块与分支比例）；
   - **硬件探索**：跨核读取外部调试 PC 采样寄存器（EDPCSR），不受 IRQ 屏蔽影响。

   上游 x86（NMI + LBR）与 arm64（ETM/SPE/BRBE）都不面对这两个失真；在 32 位产品内核上解决它们，目前没有公开方案。
5. **内存按 2 MiB 档位核算。** LPAE + STRICT_KERNEL_RWX 下内核文本按 2 MiB 段对齐：文本减少只有跨过档位才释放内存；反过来，AutoFDO 使文本增长超过余量时会一次性多占 2 MiB **[已证实（RPi4）]**。尺寸方向优先做 Thumb-2 基线与冷文件 `-Os`，并以跨档位为目标。TV 产品内核的配置未知，档位规则需拿到配置后复核。
6. **平台分工：**
   - RPi4（A72，32 位内核）：实验室主平台，K1 端到端在此进行；
   - TV SoC（Novatek NT72671D，A53，32 位内核）：产品目标，已完成 PMU 与采样探测，内核级分析等待构建信息；
   - RPi5（A76）：A76 只在 EL0 支持 AArch32，不能运行 32 位内核，只用于 arm64 路线。

## 3. 方案详述（新增与改写部分）

### 3.1 R1：IRQ 影子的度量与修正

- **问题**：关中断区间的样本落在开中断点，`_raw_spin_unlock_irqrestore`、`arch_local_irq_enable`、`finish_task_switch` 等看起来很热，调用它们的关中断热路径（调度、锁保护区）被低估。在 IP profile 中，这些调用者的内联与布局决策会偏向"冷"。
- **度量**：在每份内核 profile 的质量报告中统计 IRQ 恢复窗口份额（指令级：`cpsie i`、`msr CPSR_c` 及其后一条），并给出"C 且不在恢复窗口"的可作用份额（K1 已纳入）。
- **修正（软件）**：训练时同时记录内核调用栈（`perf record -g`，ARM32 用 unwind 表）。落在恢复点上的样本按调用栈归到调用者中调用该解锁/开中断函数的那一行；函数级热度因此得到修正，块级仍不能恢复。实现位置：llvm-profgen 新增"影子归属"选项，质量报告列出被重新归属的样本量。
- **评价**：以 R2（GCOV 执行次数）和 R3（ftrace 入口计数）为参照，比较修正前后函数热度的秩相关；再用配对测量看实际收益。
- **预期新颖性**：上游内核 AutoFDO 依赖 NMI 或硬件分支记录，没有处理这一问题。

### 3.2 R2：GCOV 计数 profile（取代 A4）

- **依据**：ARM 选择 `ARCH_HAS_GCOV_PROFILE_ALL`，`kernel/gcov/clang.c` 支持 LLVM 的 gcov 格式 **[已证实（源码）]**。可按目录或全局开启，从 debugfs 导出 `.gcda`。
- **流程**：实验室插桩构建（与 K-BASE 同源同配置，加 GCOV）→ 跑与 IP 训练相同的负载 → 导出 `.gcda` → `llvm-cov gcov` 得到行与块的执行次数 → 转换为 sample profile（按源码键：函数、相对行号；不使用 FS discriminator，因为插桩构建与被测构建的代码不同）。
- **用途**：
  1. 直接作为 profile（K-AFDO-GCOV），与 K-AFDO-IP 配对比较；
  2. 作为 R1、B1、E1 的真值；
  3. 作为 D3 的覆盖依据。
- **风险**：计数器非原子（并发下有少量丢失）；`noinstr` 与入口汇编不被插桩；插桩内核体积与开销大，只能在实验室使用；实验室负载与现场负载不一致时有偏差（这正是 B1 的用途）。
- **工作量（估计）**：1–2 周建立流程（构建、导出、转换、身份与覆盖检查），之后每次训练成本低。

### 3.3 B1：融合（改写）

- 现场设备（生产或测试中的产品）上的 IP 样本，只决定函数级的量级（哪些函数热、热多少）；
- 实验室 GCOV 计数，决定函数内的块与分支比例；
- 两者都覆盖的函数：用 GCOV 的块比例乘以现场的函数总量；只有现场样本的函数：退回 Profi 推断；GCOV 与现场热度的秩相关低于预登记阈值的函数：退回只用现场数据；
- 输出 profile 与按函数的来源和置信度报告；先在 RPi4 上用"实验室负载 = 现场负载"的情形证明融合不劣于单一来源，再用不同负载评价泛化。

### 3.4 H1：跨核 EDPCSR 采样（硬件探索）

- ARMv8 核（A53、A72）有外部调试接口的 PC 采样寄存器，由外部读取，与目标核的中断屏蔽无关。若某个核（或外部调试器）能以固定频率读取其他核的 EDPCSR，得到的样本既没有影子，也没有中断 skid。
- 前提：调试 APB 在系统地址空间中可访问，且调试授权（DBGEN/NIDEN）在目标设备上打开。RPi4 与 TV SoC 均无公开资料 **[需核实]**。
- 做法：先向 HQ/SoC 方确认地址与授权；不在未确认的地址上做试读（错误访问可能导致总线异常）。

### 3.5 尺寸与内存（改写 D1/D2，替代 C2）

- **核算规则**：报告 `.text` 原始字节、`_etext` 到 2 MiB 边界的余量、所在档位；只有跨档位的变化才算 RAM 变化。AutoFDO 使文本增长时，同样按档位报告风险（RPi4 K-BASE 余量 922,468 B）。
- **Thumb-2 内核基线**：在 ARM32 上通常是最大的文本尺寸手段 **[需核实：本内核实测]**；先只构建、量尺寸，跨档位后再做配对性能测量。
- **冷文件 `-Os`**：对所有训练负载中都没有执行的编译单元整体用 `-Os`；"没有执行"必须以 GCOV 覆盖为依据，不能以采样为依据（关中断代码会被采样漏掉）。
- **hot-cold-split**（与目标无关的 IR 层冷区外提）：替代 ARM32 上不可用的 MFS；需构建、启动与回溯验证。
- **function-sections + 符号排序 + 链接期死代码回收**：在 ARM32 上的价值需逐项证明。

### 3.6 TV SoC 的采样规则

- 用 pinned 事件；周期采样用 `r11:D`，不用 `cycles`（避免干扰 PMUMON）；
- 程序只能由 root 在 `/root` 下运行；
- 无温度读数，计时测试用频率门禁（全程记录频率，低于 1350 MHz 即标记）；
- 符号化依赖构建方提供的 `System.map` 与 `vmlinux`。

## 4. 推荐路线与门槛

| 阶段 | 内容 | 门槛 | 估计 |
|---|---|---|---|
| P1（进行中） | K1：RPi4 上 IP profile 的端到端（K1d 部署与切换、K1e 训练与 K-AFDO、K1f 配对测量）；影子与可作用份额度量 | K-BASE 启动与切换稳定；profile 质量门禁；主比较判定 | 3.5–4 周 |
| P2 | R2 GCOV 流程；R1 影子归属；以 R2/R3 评价 IP profile；K-AFDO-GCOV 与 K-AFDO-IP 对比；Thumb-2 尺寸基线 | GCOV 或修正后的 profile 质量明显优于原始 IP；尺寸手段能跨档位 | 4–6 周 |
| P3 | TV SoC：拿到构建信息后，构建 TV K-BASE，按 §3.6 采样，复用 P1/P2 的流程 | TV 内核可构建、可部署（需构建方配合） | 视配合情况 |

所有阶段沿用 workflow 规则：身份校验、正确性检查、预登记的配对测量与置信区间。

## 5. 需要 HQ 与 TV 内核构建方提供的信息

1. TV 内核（6.12.60，镜像 `T-KSU2EJAKUC-0101-PERF-202611171009`）的 `System.map` 与带 DWARF 的 `vmlinux`；
2. 构建配置：`.config`、编译器与版本、A32 还是 Thumb-2、是否 LTO；
3. PMUMON：用途、是否直接读取专用周期计数器、其数据是否被调度/温控/日志使用、能否在实验时暂停；
4. 能否在实验室 TV 板上部署自建内核（以及恢复方式）；
5. SoC 的 CoreSight 与调试 APB：是否存在、地址、调试授权状态；
6. 产品对内核最在意的场景（启动、媒体、网络、UI 响应）与内存目标的口径（内核 text、模块、整机）；
7. 产品内核升级到 6.13 及以上的计划（可直接获得上游 AutoFDO 构建支持，减少回移植）。
