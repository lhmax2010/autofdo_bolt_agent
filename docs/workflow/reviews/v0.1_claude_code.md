## 严重

### S1　A/B 对比无法证明"只差 profile"：BASE 与 AFDO 是两次独立构建，缺少工具链与编译命令的一致性门禁

**位置**：§3（BASE、AFDO 两行）、§5 S1、S5，§13。

**问题**：
- §3 断言"the A/B difference is the profile only"，但 AFDO 是在 S4 之后另起 GBS root 重新构建的，中间可能隔几天。依赖由仓库实时解析，仓库就是会被定期删除的 snapshot。
- 实测已经出现过漂移：同为 rpm-build 4.14.1.1-1.9，debugedit 的字节不同（`docs/workflow/m1/01_ffmpeg_target_build.md` §9.1）；clang 的 release 号也从 1.6 变成 4.1。
- 主机 gbs 的版本也会变化：01_release.md §9.2 记录了 2.1.0 → 2.1.1。
- 只要两次构建的工具链或依赖有任何不同，测到的差异就不能归因于 profile，而现在的设计里没有任何门禁能发现这种情况。

**建议修改**（S1、S5 增加以下规则与门禁）：
1. **冻结依赖仓库**：一个 run 的第一次构建完成后，把实际下载的依赖 RPM 存档，用 `createrepo_c` 建成本地仓库。本 run 后续所有变体（BASE、AFDO、PGOGEN、PGO、BOLT-IN）都只用这个 `file://` 仓库构建。具体做法见 I6。
2. **依赖清单一致性门禁**：每个变体的 buildroot 记录 `rpm -qa --qf '%{NAME}-%{VERSION}-%{RELEASE}.%{ARCH} %{SHA256HEADER}\n'`。BASE 与 AFDO 的清单必须逐行相同，否则 S5 失败（退出码 2）。
3. **编译命令差分门禁**：从两份构建日志提取全部 C 编译命令（M1 §8.3 已有提取器，每侧 560 条）。去掉 `-fprofile-sample-use=<path>` 后两侧必须逐条相同；`.S` 汇编命令也逐条比较。spec、源码提交与补丁的 SHA 也要相同。
4. **重建对照（建议，至少在 M1 做一次）**：在构建 AFDO 的同一冻结仓库中再构建一份 BASE，记为 BASE-r，比较 BASE 与 BASE-r 目标库的 build-id 与 SHA-256：
   - 相同：证明构建可复现，测量继续用原 BASE；
   - 不同：测量改用 BASE-r（它与 AFDO 同环境），并在报告中写明原因。
5. §3 的表述改为："A/B 的差异只来自 profile，由依赖清单、编译命令与源码三项门禁保证"。

### S2　S6 没有要求逐轮核实被测进程实际加载的库；GStreamer 插件不受 `LD_LIBRARY_PATH` 控制，按现有方案会测错对象

**位置**：§5 S2、S6；§7 GStreamer 一行；§6（包配置缺环境变量）。

**问题**：
- S2 写的是"Libraries are selected with `LD_LIBRARY_PATH`"，S6 却没有要求在测量中核实实际映射。现有 `measure.sh` 每轮调用了 `watch_maps`（`tools/profgen/board/common.sh:172–192`，`measure.sh:35`），但它只核对一个 `TARGET`，而 §6 允许多个目标库（libavcodec 与 libavutil）。
- **GStreamer 的插件**（videoconvert、videoscale）由插件扫描路径和注册表决定，与 `LD_LIBRARY_PATH` 无关。
- **注册表在变体之间共用。** 现有脚本在一个 RUN 中只设一个 `GST_REGISTRY="$RUN/registry.bin"`（`common.sh:90`），`measure.sh` 在同一个 RUN 里交替运行各个变体。两种后果都可能出现：
  - 注册表指向上一个变体或系统的插件；
  - 每次切换变体都在计时期间重扫插件。
- **FFmpeg 的私有符号不跨构建兼容。** FFmpeg 各库之间有 `avpriv_*` 私有接口，必须来自同一次构建。只换 libavcodec、其余用系统库，会得到未定义的组合。

**建议修改**：
- S6 每一轮（至少每个变体的每个批次）都读取 `/proc/<pid>/maps`，核对包配置声明的**全部**目标 DSO，以及同一软件包的其他 DSO：每个都必须来自该变体目录，SHA-256 与清单一致；任何一个来自 `/usr` 即判该轮无效，并停止运行（退出码 3）。
- GStreamer 变体按变体设置环境：
  - `GST_PLUGIN_SYSTEM_PATH_1_0=<变体插件目录>:<系统插件目录>`；
  - `GST_REGISTRY_1_0=$RUN/registry-<variant>.bin`。

  每个变体在预热轮生成注册表，正式轮设 `GST_REGISTRY_UPDATE=no`。用 `gst-inspect-1.0 --print-plugin-auto-install-info` 或 maps 核对插件的 `.so` 路径。
- 包配置增加 `[runtime] env`、`deploy_set`（必须同时来自变体目录的 DSO 集合）、`plugin_dirs` 三个字段（见 I4）。

## 重要

### I1　正确性预言机不独立，覆盖面也窄，"更快但错误"仍可能漏过

**位置**：§5 S6 Correctness；§7。

**问题**：
- **参考值来自 BASE 自己的输出。** BASE 由 clang 构建（补丁把 `CC` 改成 clang，`profiling-fix1.patch` 第 3 段），平台原包用的是平台编译器，所以 BASE 本身没有被独立验证过。
- **现有脚本连 BASE 也不固定。** `measure.sh:47–51` 用本次 RUN 中**第一轮的输出**作为期望值，这一轮可能来自任何变体。
- **覆盖面窄。** 只核对测试片段，只覆盖测试片段经过的代码路径。BBB 与 ToS 用同一套 x264 参数编码（`docs/profgen/eval/preregistration.md:8`，High profile），覆盖的解码路径基本相同。
- **核对本身干扰计时。** 每轮在计时期间用 `sha256sum` 读 FIFO（`measure.sh:33`），给计时增加了 I/O 与 CPU 负担。

**建议修改**：
1. **独立参考**：每个 run 用板上系统自带的原平台库（PLAT 角色，不需要构建）对测试输入与训练输入各解码一次，得到参考摘要。BASE 与所有优化变体都必须等于它。H.264 是位精确解码，结果不同即说明出错。
2. **一致性测试集**：每个变体在正式测量之前，另跑一次覆盖面更广的核对。可选 FATE 的 h264 一致性子集，或者 3–5 段不同编码配置的片段（Main/Baseline、CAVLC、1080p、隔行）。这一步不计时，不必每轮都做。
3. **把正确性与计时分开**：正式计时轮输出到 `fakesink`，或者把 sha256 进程绑到另一个核；正确性在专门的轮次中核对。如果坚持每轮都核对，至少把核对进程绑核，并写明它的开销。
4. 报告中写明正确性证据的覆盖范围。

### I2　S6 的温度与频率门禁在 RPi4 上不可观测，与 v1.8 §5.9 已登记的判据不一致

**位置**：§5 S0（Cooling、throttling）、S6 Per-round gates；§13 第 4 项。

**问题**：
- **节流状态读不到。** "no new throttling" 在 RPi4 上无从观测：`vcgencmd` 不存在，固件的 `get_throttled` 节点也不存在（`docs/profgen/impl/14_ffmpeg_frequency_diag.md:121`、`docs/profgen/impl/12_board_round1.md:58`、design v1.3:1291）。`common.sh:125–129` 也只能记录 `throttling=unknown`。
- **只看起始温度不够。** 门禁只检查每轮开始时的温度，测量过程中的升温看不到。
- **已有判据没有复用。** v1.x 已经登记了可逐秒观测的一组判据：`scaling_cur_freq`、`cpuinfo_cur_freq`、温度、`rpi_volt` 的 `in0_lcrit_alarm`、cycles/task-clock 有效频率协变量。v0.1 没有用它们（v1.8 原文未重读，**未核实**条款号）。
- **没有绑核。** 采样进程也没有固定在别的核上。

**建议修改**：
- 每轮在后台以 1 秒间隔记录 `scaling_cur_freq`、`cpuinfo_cur_freq`（root）、全部温度传感器与 `in0_lcrit_alarm`，采样进程绑到不跑负载的核。门禁：
  - 轮内最高温度低于 `T_load_max`；
  - 频率等于固定值；
  - 欠压告警为 0。
- 逐轮记录 cycles/task-clock（`measure.sh:37` 已有 `perf stat`）。两组有效频率的中位数相差超过 0.5% 时，报告标为"有混杂风险"。
- 负载用 `taskset` 固定到一个核（`max-threads=1` 时取 CPU3），每轮之间加固定的冷却等待。
- 节流状态在 RPi4 上固定写 `unknown`，不写成"未节流"。

### I3　统计方法没有利用交错配对，无效轮的处理会破坏配对，判定也缺"等价"一类

**位置**：§5 S6 Order、Rounds、Statistic。

**问题**：
- **没有利用配对。** 两组中位数的相对差加 bootstrap，忽略了交错执行带来的配对结构。温度与后台负载的慢漂移会同时影响相邻的 A、B，按块配对可以消掉这部分方差。
- **无效轮"重做一次，否则剔除"会破坏配对。** 剔除也可能与变体相关，例如某个变体运行时温度更高。
- **"inconclusive"混了两种情况。** 置信区间完全落在 ±ε 之内（证明差异小于 ε）与区间太宽，现在都叫 inconclusive，Agent 无法区分。
- **小样本下 percentile 区间偏窄。** n ≈ 10 时 percentile bootstrap 偏窄，v1.x 已登记为已知局限。

**建议修改**：
- 统计单位改为"块"，每块是一轮完整的交错。对每块计算 r_i = ln(t_AFDO,i / t_BASE,i)，同时给出 t 区间与 bootstrap 区间，两者都满足才下判定。报告中写明换算 exp(r) − 1。
- 无效块在全部块结束后重跑，上限为 N 的 20%。超过上限，或者无效原因与变体相关时，整次运行判 inconclusive，并列出原因。
- 判定分四类：
  - faster：上界 < −ε；
  - slower：下界 > +ε；
  - equivalent：区间在 (−ε, +ε) 之内；
  - inconclusive：其他情况。
- 三个以上变体时，每个变体只与 BASE 比较，报告中注明这是多重比较、没有校正。
- 保留"达到 N 之后不再加轮"，这一条是对的。

### I5　BOLT 路径：Tizen 打包默认会剥掉 BOLT 需要的节；预聚合模式不校验身份

**位置**：§3（BOLT-IN、BOLT 两行）、§5 BOLT path 第 2–4 步、§10 M4。

**问题与依据**：
1. **打包会剥掉 BOLT 需要的节。** Tizen 的 `find-debuginfo.sh` 对共享库默认执行 `eu-strip --remove-comment -f`，不带 `-g`（`strip_g=false`，第 69 行；`strip_to_debug` 在第 248–282 行，位于 M1 armv7l root 的 `/usr/lib/rpm/find-debuginfo.sh`）。它会删除 `.symtab` 与 `--emit-relocs` 产生的非分配节 `.rela.text`。设计只提到"keep or re-attach the symbol table"，没有提到重定位节。
   - 可用的开关是 `--define '_rpm_strip_disable 1'`，经 `/usr/lib/rpm/macros:178` 展开为 `--strip-disable`（`find-debuginfo.sh:147–148、254`）。
   - aarch64 root 与其他 install_post 步骤**未核实**。
2. **预聚合模式不校验身份。**
   - `--pa` 模式下，`buildid:offset` 格式中的 build-id 只被解析，不用于校验：`DataAggregator.cpp:1245–1266` 解析后，`:1360–1371` 直接拿 `Offset` 当地址，传给 `getBinaryFunctionContainingAddress`。所以身份过滤只能由转换器做。
   - 写入的值必须是 ELF 虚拟地址，不是 `dsoff` 文件偏移。
3. **必须带 `-ba`。** `S` 记录只有在 `-ba` 下才会被处理（`processProfile`，`:651–654`），不能省略。
4. **build-id 区分不了 BOLT 与 BOLT-IN。** BOLT 输出沿用输入的 build-id（**未核实**，M4 实测确认），所以变体身份只能用 SHA-256 区分。
5. **比较对象。** BOLT-IN 不剥离、带重定位节，与 BASE 不同，应比较 BOLT 与 BOLT-IN，而不是与 BASE。
6. **当前源码不拒绝 AArch64 共享库**（`RewriteInstance.cpp:405–410` 只打印信息），但只在重定位模式下完整支持（`:2280–2282`）。

**建议修改**：
- 第 2 步写明：BOLT-IN 构建加 `--define '_rpm_strip_disable 1'`。门禁：部署文件的 `readelf -S` 中有 `.symtab` 与 `.rela.text`；`llvm-bolt` 日志中没有 non-relocation 警告。
- 第 3 步写明：转换器按 build-id 过滤、把 `dsoff` 换算为虚拟地址（按 PT_LOAD），输出纯地址，不依赖 perf2bolt 校验；命令固定为 `perf2bolt --pa -ba`。
- S6 中 BOLT 的比较对象改为 BOLT-IN，身份按 SHA-256。
- 转换器的单元测试增加：其他 DSO 的样本被过滤；`dsoff` 与虚拟地址不同的 PT_LOAD；build-id 不符时拒绝。

### I6　snapshot 删除：设计没有对策，现有存档也从未验证过离线复建

**位置**：§5 S1，§13。

**事实**：
- 板子镜像对应的 snapshot 已经 404（M1 §7.1，`20261104.160709`），只能按规则回退到其他固定 ID。
- 已有存档：`temp/gbs-deps-archive/ffmpeg-armv7l-20261114/`，108 个 RPM，271,003,299 B。但离线复建从未执行过：M1 §7.4 与 `01_release.md` §9.5 都标着"示例，未执行"。

**建议对策**（写进 S1 与 §2）：
1. **按变体的并集存档。** S1 一次性解析本 run 全部计划变体的依赖并集，然后存档。PGOGEN 可能需要额外的 compiler-rt profile 运行时包，它所在的 RPM **未核实**，只存 BASE 的依赖可能不够。存档写入 SHA 清单，记录来源 snapshot ID 与解析时间。
2. **本 run 只用存档构建。** 全部变体只用 `createrepo_c` 生成的 `file://` 仓库（与 S1 第 1 条一致）。在线仓库只用于第一次解析。
3. **M1 验证一次离线复建。** 在新 root 中只用存档重建 BASE，核对目标库的 build-id 与 SHA 和原 BASE 相同（同时满足 S1 第 4 条）。

## 一般

### G1　S5 的 Profi 与覆盖诊断（回答 §13 第 2 项）

- **Profi 的条件写得不准。** 只要命令行有 `-fprofile-sample-use`，驱动就会加 `-mllvm -sample-profile-use-profi`，除非显式给了 `-fno-sample-profile-use-profi`（`Clang.cpp:6276–6281`）。这与是否 LTO 无关，所以"on for non-LTO"应改为"驱动默认打开"。
- **覆盖诊断的选项名已确认**：
  - `-mllvm -sample-profile-check-record-coverage=N`
  - `-mllvm -sample-profile-check-sample-coverage=N`

  两者默认都是 0，即不检查；只有覆盖率低于 N% 时才逐函数告警（`SampleProfileLoaderBaseUtil.cpp:26–34`）。要收集数据，就把 N 设为 100，再从构建日志中解析每条告警。另有 `-mllvm -report-profile-staleness`（`SampleProfile.cpp:143`）。
- 只有给 AFDO 变体传这些选项，才不会破坏 S1 的编译命令差分：差分时连同 `-fprofile-sample-use` 一起去掉。

### G2　S0 的 cycles 检查（证据）

两块板以往都记录到 `cycles: type: 0 (PERF_TYPE_HARDWARE) ... config: 0`：RPi5 见 `docs/probe/evidence/17_rpi5_sampling.txt:674`，RPi4 见 `temp/board-round1-patch8/runs/*/evlist.txt`。检查可以保留，但建议：
- 按事件名、type、config 三项一起解析；
- 同时核对 perf 的 SHA 与 `perf version`（RPi5 为 6.12.80）。

### G3　手写汇编不被 AFDO 覆盖，收益上限应写入报告

M1 中每侧有 54 条 `.S` 汇编命令，不带 profiling 选项（M1 §8.3）。NEON 汇编中的热点既不能被采样归属到源码行，也不会被 AFDO 优化。

建议 S7 报告目标 DSO 中三类样本的占比，作为预期收益的上限说明：有 DWARF 的 C 代码、汇编、`outside_dwarf_func`。这三项可以直接取自 profgen 质量报告。

### G4　GStreamer 的目标选择应以数据为依据（回答 §13 第 3 项）

- §7 的 GStreamer 管线包含 `avdec_h264`，大部分时间会花在 libavcodec 上，而它属于 FFmpeg 包，会稀释 GStreamer 的收益。
- videoconvert、videoscale 的热循环可能由 ORC 在运行时生成。Tizen 是否启用 ORC **未核实**；如果启用，这部分样本落在匿名内存中，无法优化。

建议：
- M3 先做一次热点普查：用 BASE 管线采样，列出各 DSO 的样本占比，再确定目标。
- 测量管线改用原始视频输入，例如 `filesrc` 读 I420 文件，或 `videotestsrc` 加固定 pattern，避免解码占主导。
- 如果 ORC 生效，两种取舍都要在报告中写明：保持生产配置并接受较小的收益，或者两侧都设 `ORC_CODE=backup`（但那测的就不是生产配置了）。

### G5　§3 的 PGO 变体定义与实际 spec 补丁不一致

- **定义不一致。** 补丁让 `profile_flags`（`-fdebug-info-for-profiling -funique-internal-linkage-names`）无条件进入 CFLAGS，而 §3 把 PGOGEN、PGO 定义为"Platform flags + …"。
- **建议的定义**：PGOGEN = BASE + `-fprofile-generate`，PGO = BASE + `-fprofile-use`，并在补丁中增加对应的宏，这样 PGO 与 BASE 也只差 profile。
- **链接参数未核实。** FFmpeg 的链接步骤是否带上 `-fprofile-generate`（链接 profile 运行时）**未核实**，需要放进 `--extra-ldflags`。S1 增加门禁：PGOGEN 的目标库中存在 `__llvm_profile_runtime` 等符号。
- **核对 profraw 能对应到目标库。** `common.sh:92` 已经为插件扫描阶段设置了 setup 用的 profraw 路径。训练时需要核对每个 profraw 都能对应到目标 DSO，`%m` 的用法正确。
