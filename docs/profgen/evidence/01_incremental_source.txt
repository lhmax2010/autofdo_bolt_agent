912: '''''''''''''''''''
914: Starting from gbs 0.10, the gbs build subcommand supports building incrementally, which can be enabled by specifying the '--incremental' option.
916: This mode is designed for development and verification of single packages. It is not intended to replace the standard mode. Only one package can be built at a time using this mode.
918: This mode will set up the build environment in multiple steps, finishing by mounting the local Git tree of a package in the chroot build environment.
920: **Note**: Because gbs will mount your git tree to the build root, be very careful when you remove your build root. You need to make sure you've already umounted the source tree manually before you remove it.
922: This has the following benefits:
924: 1. The build environment uses the latest source code and changes to source do not trigger a new build environment (in the chroot).
925: 2. The Git source tree becomes the source of the builds.  Any change made in the Git repository followed by invocation of the build script will build the changed sources
926: 3. If the build fails for some reason, the build script will continue from the spot where it has failed, once the code has been changed to fix the problem causing the failure.
928: This mode is, in many ways, similar to traditional code development, where changes are made to sources, followed by running `make` to test and compile the changes. However, it enables development using the build environment of the target, instead of the host OS.
930: This method has some limitations, mostly related to packaging and how the sources are maintained.  Among others, it depends on how the RPM spec file is composed:
932: 1. It does not support patches in the spec file. All source has to be maintained as part of the Git tree
933: 2. It requires a clean packaging workflow.  Exotic workflows in the spec files might not work well, because this mode expects the following model:
935:    a. Code preparation (%prep)
936:    b. Code building (%build)
937:    c. Code installation (%install)
939: 3. Because we run the %build section every time, if the %build script has configuration scripts (auto-tools), binaries might be regenerated, causing a complete build every time.  To avoid this, you are encouraged to use the following macros, which can be overridden using the `--no-configure` option:
941:    a. %configure: runs the configure script with pre-defined paths and options.
942:    b. %reconfigure: regenerates the scripts and runs %configure
943:    c. %autogen: runs the autogen script
1001: From the buildlog, we can see that only log.c has been re-compiled. That's the incremental build behavior.
1003: `--noinit` option can be used together with `--incremental` to make a build more quickly, like:
1005: ::
1007:   $ gbs build --incremental --noinit
