# ARM（armv7l 为主、aarch64 为辅）内核 AutoFDO 能力增强方案 v0.1（供评审）

| 项目 | 内容 |
|---|---|
| 版本 | v0.1，评审稿 |
| 目标 | 用我们的 AutoFDO 方案让 Linux 内核**更快、占用内存更少**；首要平台 armv7l（32 位 ARM 消费类产品），其次 aarch64 |
| 范围 | profile 来源（硬件/软件）、profile 转换（llvm-profgen）、内核构建与消费、内存优化、验证方法。BOLT 不在本文范围（不支持 32 位 ARM） |

## 0. 结论先行

1. 只靠普通 IP 采样，内核 AutoFDO 的上限有限：IP 样本只给"热度"，不给分支方向与边频率，而内核收益主要来自布局与分支方向（前端停顿）。要做得比市面方案更好，必须在 ARM32 上**补出分支信息**。
2. 32 位 ARM 没有 LBR、SPE、BRBE，这三种硬件无法"移植"。能补分支信息的路线有四条，本文按可行性排序提出：
   - **A2 被采分支目标采样（新方案）**：用 PMU 的"已执行跳转/PC 写入"事件采样，样本 PC 近似落在跳转目标上，统计得到基本块入口频率。只需 PMU，ARM32 现有板子即可试验。
   - **A4 采样式插桩 PGO（实验室设备）**：内核插桩 PGO + LLVM 的采样插桩，得到接近真值的边计数，作为高质量 profile 或校准源。
   - **A3 CoreSight ETM 的 ARM32 适配**：硬件有 ETM 时最好，但取决于产品 SoC 是否暴露 CoreSight 与 trace sink；我们两块板子都没有。
   - **A5 pseudo-probe（CSSPGO）用于 ARM32**：改善源码变动后 profile 的复用，需要先修 ARMv7 上的 clang 崩溃。
3. 创新点放在"融合"：**B1 混合 profile**——生产设备上低开销的 IP/分支目标样本给"哪里热"，实验室设备上的插桩或 ETM 数据给"分支怎么走"，在 llvm-profgen 中合成一份 profile，并输出可判定的质量报告。
4. "更少内存"不会自动发生：AutoFDO 本身倾向于让热路径变大。要减少内存，需要配套的**D 组**：冷代码按尺寸优化（PGSO）、冷热拆分、热代码聚集，以及用多设备 profile 找出从未执行的代码供裁剪决策。每项都要实测尺寸与性能的取舍。
5. 建议路线：先做 **C1（内核 AutoFDO 构建回移植 + ARM32 启用）+ A1（内核 IP profile）+ A2 探针 + D1/D2 尺寸测量**，用实验室插桩（A4）作为真值来评价所有来源；A3 等产品 SoC 信息后决定。

## 3. 方案详述

### A1 内核 IP 采样 profile（补齐）

- 原理：system-wide `perf record -e cycles -a`，导出包含内核 mmap 的 perf script；llvm-profgen 用内核锚点（`_text`/`_stext`）把运行地址换算到 vmlinux 链接地址，DWARF 符号化，生成 vmlinux profile。
- 改动：上游 llvm-profgen 的内核路径只服务 LBR **[外部]**；把它接入我们的 IP 模式：内核身份（vmlinux build-id）、锚点换算（ARM32 通常无 KASLR，arm64 有）、pid −1、kernel/user 分离；模块（ET_REL）放后续。
- 风险：IP 只给热度，分支方向靠编译器推断，收益可能明显低于上游 x86 数字。
- 工作量（估计）：中，约 1～2 周设计 + 实现 + 测试。
- 验证：与 A4 真值比较热函数覆盖；内核基准的配对测量。

### A2 被采分支目标采样（新方案）

- 原理：ARM PMU 有"已执行的跳转"（BR_RETIRED，0x21）与"软件改写 PC"（PC_WRITE_RETIRED，0x0C）等通用事件 **[需核实：A72 AArch32 下的可用性与计数语义]**。以这类事件做采样时，溢出中断在跳转执行后发生，记录的 PC 在跳转目标附近。若 skid 小且可校正，样本分布≈各基本块的**入口频率**；与 cycles 样本（块内停留时间）结合，可估计每个块的执行次数与部分边频率，正好补 IP 采样缺的信息。
- 为什么新：上游 IP RFC 的讨论中有人提过"采样已退休跳转事件来改善块权重"，但没有实现与评估 **[外部]**；在 ARM32 上把它做成 profile 来源并以真值校准，目前没有公开结果。
- 改动：llvm-profgen 新增"跳转目标样本"输入类型：把样本 PC 归到所在块的块首（需 ARM/Thumb 块边界，用 B3 的反汇编）、对 skid 建模（离块首的距离分布）、输出块入口计数；与 cycles 样本联合推断。
- 探针（便宜、先做）：用户态 FFmpeg（已有插桩 PGO 能力，M2b）先做：同一负载分别采 cycles、BR_RETIRED/PC_WRITE_RETIRED 样本与插桩真值，计算"样本 PC 落在块首附近的比例"和"块入口计数与真值的相关性"。
- 风险：skid 大或随核变化时，样本无法可靠归到块；PMU 中断开销。门槛：若块首命中率与真值相关性不达标，止损。
- 工作量（估计）：探针 3～5 天；实现 2～3 周。

### A3 CoreSight ETM 的 ARM32 适配

- 两种情况：
  - 真正的 ARMv7 核（Cortex-A7/A9/A15/A17）：内核已有 ETMv3/PTM 驱动支持 32 位 **[已证实（源码阅读）]**，需要 SoC 设备树描述 CoreSight 组件与 sink（ETB/ETF/ETR）。
  - ARMv8 核（A53/A55/A72/A76）运行 32 位内核：ETMv4 驱动限 ARM64 **[已证实]**；需要移植到 ARM32 内核（ETMv4 有内存映射寄存器访问方式，难点在系统寄存器路径与 ETE/TRBE 相关代码的隔离）**[需核实]**。
- 数据链：`perf record -e cs_etm//k` → `perf inject --itrace=il64` 合成分支栈样本 → llvm-profgen 现有分支路径（需 B3 的 ARM32/Thumb 支持）。OpenCSD 能解码 A32/T32 **[外部]**，perf 对 32 位程序的解码是否完整 **[需核实]**。
- 前提：产品 SoC 必须把 CoreSight 接到可用的 sink，且量产设备未关闭调试授权（DBGEN/NIDEN）**[需核实，向 HQ 要 SoC 信息]**。数据量大，需要 strobing 或短窗口。
- 风险：我们两块板子都没有 ETM，无法自行验证；需要 HQ 提供带 ETM 的开发板。
- 工作量（估计）：驱动移植 2～4 周（若需要）；数据链与 B3 共享。

### A4 内核采样式插桩 PGO（实验室真值）

- 原理：内核用 `-fprofile-generate` 构建并在内核内提供 profile 运行时（导出 profraw），在实验室设备上跑代表性负载，得到边计数真值；用 LLVM 的采样插桩降低开销 **[需核实：采样插桩选项名称与对 ARM32 内核的适用性]**。
- 来源：2021 年曾有内核 Clang PGO 运行时补丁（kernel/pgo）进入过 linux-next 后撤回 **[需核实]**；需要回移植到 6.12 并适配 ARM32。
- 用途：
  1. 直接作为高质量 profile（实验室负载代表产品负载时）；
  2. 作为 E1 的真值，评价 A1/A2/A3/B1；
  3. 作为 B1 的分支方向来源。
- 风险：插桩内核体积与开销大，只适合实验室；运行时补丁维护成本。
- 工作量（估计）：3～4 周。

### A5 pseudo-probe IP（CSSPGO）用于 ARM32

- 原理：pseudo-probe 让 profile 按"块探针"而非行号匹配，源码小改后仍可复用；与 IP 样本结合可更准确地归块。
- 现状：ARMv7 上 pseudo-probe 编译有已知 clang 崩溃 **[已证实]**。
- 工作量（估计）：先定位并修复崩溃（1～2 周），再评估收益。优先级低于 A2/A4。

### B1 混合 profile 融合（核心创新）

- 原理：生产/测试设备上大量低开销样本（A1 cycles、A2 跳转目标）决定"哪些函数、哪些块热、热多少"；实验室设备上少量高质量数据（A4 插桩或 A3 ETM）决定"热块之间分支怎么走"。llvm-profgen 读入两类输入：
  - 函数与块的总量取自生产样本（代表真实使用）；
  - 分支概率取自实验室数据，按函数/块映射到同一二进制（要求同一构建或可映射的构建，身份校验沿用现有规则）；
  - 生产样本里热、实验室数据里没覆盖的区域，回退到 Profi 推断（B2）。
- 输出：一份 sample profile + 质量报告（每个函数的数据来源、覆盖率、置信度）。
- 为什么新：上游方案都假设单一来源（LBR、SPE 或 ETM）；"热度来自现场、方向来自实验室"的融合目前没有公开实现。
- 风险：实验室负载与现场负载的分支行为不同时，方向信息会误导；需要 E1 评估并设置回退规则。
- 工作量（估计）：3～4 周（依赖 A4 或 A3 至少一个可用）。

### B2 IP 专用的流量推断先验

- 原理：LLVM 的 Profi 根据块计数推断满足流守恒的边计数。IP 样本给的是"停留时间"而不是"执行次数"，长延迟指令所在块会被高估。可用每块指令数、指令类别、A2 的入口计数作为先验，改进推断。
- 验证：与 A4 真值比较边计数误差。
- 工作量（估计）：2～3 周，偏研究。

### B3 llvm-profgen 的 ARM32 分支路径

- 原因：现有分支（LBR）路径依赖全量反汇编，在 Thumb 与 `$d` 数据区上会出错 **[已证实（设计阶段分析）]**；A2、A3、A4 的数据要进入它，必须先支持 ARM32。
- 改动：复用 IP 模式已实现的映射符号与 Thumb 指令长度逻辑。
- 工作量（估计）：1～2 周。

### C1 内核 AutoFDO 构建回移植 + ARM32 启用

- 内容：回移植上游 AUTOFDO_CLANG 的构建支持（Makefile.autofdo、arch/Kconfig、vmlinux.lds.h 中 .text.hot/.text.unlikely/.text.split 的放置）到 linux-rpi 6.12；为 ARM（及需要时 arm64）新增 select 并修改 arch/arm/kernel/vmlinux.lds.S。
- 风险：链接脚本与启动代码对节顺序的假设；Thumb-2 内核配置（若启用）的特殊性；模块链接。
- 依赖：K0 的回移植与冲突分析。
- 工作量（估计）：1～2 周 + 板上启动验证。

### C2 ThinLTO 与机器函数拆分（MFS）

- 上游内核 AutoFDO 系列包含 ThinLTO 与 MFS 支持 **[外部]**；MFS 在 ARM 32 位后端是否可用 **[需核实]**，ARM32 内核 ThinLTO 是否被 Kconfig 允许 **[需核实]**。
- 若可用，MFS 把热函数里的冷块拆到单独节，配合 D2 降低 I-cache/iTLB 压力。

### D1 profile 引导的冷代码尺寸优化（PGSO）

- 原理：有 profile 时，LLVM 可对冷函数和冷块按尺寸优化（PGSO）**[外部，ARM32 实际行为需核实]**；进一步可以把从未采到样本的函数整体按 minsize 编译。
- 目标：内核 text 与模块体积下降，同时热路径保持速度优化。内核 text 常驻内存，所以 text 体积下降直接等于内存下降。
- 风险：无样本 ≠ 冷（采样覆盖不全）；须用多负载、多设备 profile（D3）与 A4 真值决定"冷"的门槛。
- 验证：`size vmlinux`、各模块 `.text` 体积；内核基准不退化。

### D2 冷热拆分 + 热代码聚集

- 内核：热函数集中到 .text.hot，减少 iTLB/I-cache 未命中（速度收益）；内核 text 常驻，此项对内存帮助小。
- 用户态（附带收益）：共享库的代码页按需加载，把热代码集中在少数页、冷代码集中在其他页，可减少常驻页数（RSS）。FFmpeg/GStreamer 可直接验证（/proc/pid/smaps 中的 Rss）。
- 工作量（估计）：主要是构建参数与测量，1 周。

### D3 多设备覆盖率汇总（内存裁剪建议）

- 原理：汇总多台设备、多种负载的内核 profile（及 A4 插桩覆盖），列出"在所有场景中从未执行"的函数、子系统与模块，按体积排序，作为内核配置/模块裁剪的**建议**（由内核 owner 决定，不自动删除）。
- 为什么新：AutoFDO 数据通常只用于优化编译；把它用作"内核瘦身的证据"在嵌入式设备上能直接减少内存。
- 风险：罕见路径（错误处理、恢复、安全相关）采不到但不能删；报告必须把这类代码标出来，只能作为参考。

### E1 profile 质量评价

- 以 A4 插桩真值为基准，对 A1/A2/A3/B1/B2 计算：热函数覆盖、块计数相关性、边计数误差、按函数的分支方向一致率；再用 workflow 的配对测量看实际收益。先在用户态（FFmpeg，已有插桩 PGO 能力）做，再搬到内核。

## 4. AArch64 方案能否转成 ARM32

| AArch64 / x86 方案 | 依赖 | 能否转到 ARM32 | 本文对应 |
|---|---|---|---|
| SPE 统计采样 | ARMv8.2+ 硬件 | 否（硬件特性） | 用 A2 近似其"分支统计"作用 |
| BRBE 分支记录 | ARMv9.2 硬件 | 否 | — |
| LBR / AMD BRS | x86 硬件 | 否 | — |
| ETM AutoFDO（arm64 现有流程） | CoreSight ETM + sink | 有条件：ARMv7 核可直接用；ARMv8 核运行 32 位内核需移植 ETMv4 驱动 | A3 + B3 |
| 内核 AUTOFDO_CLANG 构建支持 | 编译器 + 链接脚本 | 可以，需新增 ARM 启用 | C1 |
| Propeller（基本块段） | 分支数据 + 后端支持 basic-block sections | 后端支持 **[需核实]**，且需要分支数据 | 暂不列入 |
| BOLT | x86/AArch64/RISC-V | 否 | — |
| 内核插桩 PGO | 内核运行时 + 编译器 | 可以，需回移植并适配 | A4 |
| CSSPGO pseudo-probe | 编译器 | 可以，需修 ARMv7 崩溃 | A5 |

## 5. 推荐路线与门槛

| 阶段 | 内容 | 门槛（不过即止损或调整） | 估计 |
|---|---|---|---|
| P0（与 M1 并行，主机侧） | K0 可行性；C1 回移植检查；A2 探针在用户态 FFmpeg 上做（需 RPi4，M1 结束后）；D1/D2 在用户态先测尺寸与 RSS | K0 结论非 no-go；A2 块首命中率与真值相关性达到预设门槛 | 1～2 周 |
| P1 | C1 完成并在 RPi4 启动；A1 内核 IP profile；内核基准（网络回环、系统调用、管道/调度、文件 I/O）配对测量；D1 测内核 text 体积 | 内核在目标负载中的时间占比足够；IP-only 有可测收益或尺寸收益 | 3～4 周 |
| P2 | B3 + A2 实现；A4 内核插桩真值；E1 质量评价 | A2 或 A4 的 profile 质量明显优于 A1 | 4～6 周 |
| P3 | B1 融合；B2 推断改进；D3 裁剪建议；A3（拿到带 ETM 的产品板后） | 融合 profile 的收益高于单一来源 | 4～6 周 |

所有阶段沿用 workflow 的规则：身份校验、正确性 oracle、预登记的配对测量与置信区间；每个方案的结论必须有数据。

## 6. 需要 HQ 提供的信息

1. 目标产品的 SoC 与 CPU 核（ARMv7 核还是 ARMv8 核运行 32 位）、内核版本、是否 clang 构建。
2. 产品内核是否暴露 PMU；SoC 是否有可用的 CoreSight ETM 与 sink；是否有可开调试的开发板。
3. 对内核最在意的场景（网络、存储、启动、应用启动、媒体驱动）与可用的基准。
4. 内存目标的口径：内核 text、模块、还是整机 RSS。

## 7. 请评审重点回答的问题
