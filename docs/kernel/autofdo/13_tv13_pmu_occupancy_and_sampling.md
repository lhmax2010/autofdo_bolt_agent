# TV 板 .13：PMU 占用与两段 cycles 采样

2026-11-18（America/Los_Angeles），SDB 目标 `192.168.108.13:26101`。未运行 perf 的 10.23 秒内，四核 PMU 中断均增长，内核亦周期性输出 `[PMUMON]` 四核计数摘要。普通进程级硬件事件被启用但 running 为 0，进程级 pinned cycles 和 CPU3 级事件取得读数。两段系统级采样通过本轮共用判据，内核样本份额分别为 **86.5300%** 和 **91.0703%**。 [上一轮报告](12_tv13_root_perf_pmu_sampling.md) · [本轮证据索引](evidence/13-tv13-pmu-occupancy/index.json)

## 共享板基线和判据

用 root 采集 61 帧进程快照，首尾相隔 **309.38 秒**，相邻约 5.15 秒。每帧记录 uptime、loadavg、PID、PPID、用户、ps %CPU、累计 CPU 时间和 comm，从 PPID 重建父链。ps %CPU 为进程生命周期平均值。基线 load1 为 28.42–28.85。完整基线保留在主机 temp，证据索引记录路径和 SHA。

`acm-watcher` 在 61 帧中出现 60 帧，共 7 个 PID，用户为 owner。所见 cmdline 为 `/usr/bin/acm-watcher`，父链为 acm-watcher → PID 1131 的 owner systemd → PID 1 的 root systemd，cgroup 为 `/user.slice/user-5001.slice/systemd-user-sessions.service/acm-watcher.service`。基线 ps %CPU 为 0.0–2.7%。据此将其归为板上已有的 systemd 用户服务，不能单凭它的 CPU 波动判定他人操作或丢弃。 [基线摘要](evidence/13-tv13-pmu-occupancy/baseline-summary.json)

每阶段前记录 SDB 设备和进程状态。运行期间以任务 shell、观察脚本和工作进程的 PID 为根，按快照 PPID 排除自身后代。只有外部 sdbd 后代、新出现的测试/调试进程，或主机观察到其他 SDB 客户端操作才标记。系统守护进程的 CPU 偏移在结果的 `system_cpu_excursions` 中另列。SDB devices 本身只列设备状态，不能显示命令执行，需要与主机 SDB 客户端轮询和板上父链合用。短于轮询间隔或已脱离父链的命令仍可能漏见。两段采样均无标记，无补采。board 监控会产生少量自身用户及内核活动，系统级份额包含这部分背景。

部署复用上一轮 SHA 已核对的 perf 6.12.80、两项依赖和静态 A32 程序，脚本也逐个核 SHA。任务目录 `/root/afdo_probe-tv13-20261118` 创建前登记，`/lib/ld-linux.so.3 --list ./perf` 与 `perf --version` 均通过。基线结束时先恢复 root off，正式诊断另起 root 会话，避免准备脚本时持续持有 root。

## 内核内 PMU 活动

无本任务 perf 的区间前、中、后 `ps -C perf` 均空，主机未观察到其他 SDB 客户端操作。两次 `/proc/interrupts` 读取在板上 uptime 161305.06–161315.29 之间。IRQ 41–44 在 CPU0–3 上的增量分别为 **1、2、2、2**。dmesg 的 `[PMUMON]` 约每 5 秒记录每核 Core、IPC、Stall、BW，和一直存在的 PMU 活动相符。证据支持内核内已有 PMU 使用者，**PMUMON 是目前可辨认的使用者**。未追踪其每个事件的来源，也未将全部中断归给 PMUMON。

当前 ring buffer 无 `hw perfevents` 启动初始化行，物理计数器数量无日志可核。所列候选模块包含 `softirq_monitor` 和名称碰巧匹配的 `usb_common`、`videobuf2_common`，未发现同名 PMUMON 已加载模块。不能由此断定它是何种链接方式。相关 sysfs 有 `/sys/devices/platform/pmu` 和 `armv7_cortex_a7`。所查 pmu/perf procfs 与 PMU debugfs glob 无匹配。

root `CapEff=000001ffffffffff` 含 CAP_SYSLOG（bit 34）及 CAP_PERFMON（bit 38）。本轮 root 读取 `/proc/kallsyms` 返回 **No such file or directory**。上轮没有取得非零地址且没有板上退出哨兵，本轮证据为接口缺失，无法归因于 kptr_restrict 或 CAP_SYSLOG 缺失。未读到地址表内容，未改变设置。 [命令与原始日志](evidence/13-tv13-pmu-occupancy/transcripts.json.gz)

### r0c 与 r08 的 A/B

A、B 均固定每轮 N=67,108,864，已采纳分支各 67,108,863。B 额外加入 N 次未采纳条件分支。进程级 r0c、r08 均不运行，改用 CPU3 级读数。A/B 墙钟分别约 59.58、118.97 ms，按各自 enabled/running 线性估计：

| 指标 | A | B | 解释 |
|---|---:|---:|---|
| r0c 估计 | 70,208,394 | 69,245,375 | 比已采纳数高 4.62%、3.18%，B/A=0.9863 |
| r08 估计 | 143,282,277 | 281,238,819 | B/A=1.9628，接近动态指令槽预期的两倍 |

r0c 在 B 多出约 6711 万次未采纳分支时没有成比例增加，**支持 r0c 主要追踪已采纳分支**。CPU 级同时计入其他任务，2 秒 sleep 背景也有 r0c/r08 读数，且本次每版只一次、实际复用覆盖不满。因此不能把这组结果当成 r0c 只计已采纳分支的严格证明，也不能把 r08 按指令槽估计当作退休定义。r21 未在本轮重新诊断。 [详细结果](evidence/13-tv13-pmu-occupancy/result.json)
