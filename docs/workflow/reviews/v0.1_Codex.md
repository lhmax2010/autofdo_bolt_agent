## 2. 严重问题

### S1 — S6 的统计量、顺序和失效轮次没有形成同一个可实现的比较契约

**位置：**W §5/S6，119–124；§6 `[measure]`，186–192。

**问题：**固定 `A B A B` 让变体与运行位置绑定；“median relative difference”没有说明是中位数之比还是逐对相对差的中位数，bootstrap 也没有抽样单元、次数或配对规则。“不够合格就重试一次，否则剔除”可能分别筛选 A/B，留下不同的比较总体。`better="higher"` 又没有对应的判读公式。

**理由：**即使没有编译优化效应，如果每块第一个位置耗时 100、第二个位置因缓存或环境效应耗时 98，固定 AB 也会稳定给出约 −2%；区间再窄也不能消除位置混杂。按变体分别删除高温或失败轮次还可能删除优化造成的真实代价。现有 `board/measure.sh:24–27` 至少轮转顺序，不能把新设计的固定 AB 当作更充分的方案；该旧脚本固定十轮，也不能直接当作新 N/CI 实现。

**建议修改：**在 S6 写入以下具体规则，不混用 v1.8 的质量统计规则：

> 测量前锁定 N 个 block、输入、预热、顺序及种子。每个 block 包含全部比较变体；两变体采用预先生成、尽量平衡的 AB/BA，多变体采用平衡轮转并保存实际表。各变体每个 block 恰好贡献一个正式值。时间指标主估计量为 `δ = median(T_candidate) / median(T_control) - 1`；以完整 block 为单位联合重采样所有变体，20,000 次 percentile bootstrap，保存种子与实现版本。CI 上界 `< -ε` 为 faster，下界 `> +ε` 为 slower，其余 inconclusive；不把 inconclusive 称为等价。其他方向的指标必须另行定义变换，M1 只接受正的耗时秒数。
>
> N 是预定正式 block 数，不是“补足 N 个干净结果”。完整返回的原始轮次及异常标签均保存，不能用更干净的重试替换原结果。只有预先列明的、没有取得有效测量值的技术故障允许整个 block 重试一次；原尝试仍保存。正确性失败直接失败。缺失正式 block 时只给现有数据的诊断统计，主结论为 incomplete/inconclusive；不得分别缩小 A/B 后宣布收益。遥测干净子集按完整配对 block 做敏感性分析，不能代替预定主结果。

同时明确：N 公式只是近似预算，不保证功效或 CI 半宽；正式结果不能触发增轮。多个输入、变体若择优宣布包级收益，应预定一个主比较/汇总；其余报告逐项 CI 并标为探索性，不把“任一显著”当作包级证明。

**验收：**固定位置效应的合成序列；N 为奇数时 AB/BA 数差不超过 1；共同时间漂移；同一 block 的协方差；A/B 单边缺失；高温值不能被重试替换；N 到点仍不确定；恰好等于 ±ε；零值、NaN、Infinity；higher 指标未实现时拒绝配置。

## 3. 重要问题

### I1 — 缺少构建锁和 snapshot 消失后的双轨处理，无法保证 A/B 只差 profile

**位置：**W §2.3、S0、S1、S5、§9。

**问题：**工具 SHA 和产物 SHA 不能证明两次构建使用相同源码、依赖、编译器、spec、路径与参数。固定 snapshot URL 也不是持久存档。若 BASE 构建后 snapshot 消失，AFDO 自动改用新 snapshot，就破坏了 A/B。

**依据：**`delivery/01_release.md:97–105,274–312,352–370` 记录真实 404、116/122 依赖不同及归档，但离线复建尚未验证。M1 `01_ffmpeg_target_build.md:325–335` 甚至记录相同 rpm-build 版本/release 的 debugedit 字节不同。`CodeGenModule.cpp:508–518` 对源文件路径生成 unique-internal-linkage 后缀，因此路径变化也可能让消费失配。

**建议修改：**

> S0/S1 生成 `build-lock.json`：源码 commit 与完整 overlay/未提交差异 SHA、spec/宏、实际编译/链接工具及加载依赖 SHA、编译命令、ISA/CPU/ABI、构建系统配置、源路径规范、GBS 版本和实际 buildconf、snapshot URL/元数据 SHA、实际依赖 RPM 的 NEVRA+SHA+来源。BASE/AFDO 在除声明的 profile 消费参数外逐项一致；消费 profile 在 chroot 内以固定只读路径 staging 并核验 SHA。检查真实 C/C++/汇编/链接命令，不只检查宏字符串。
>
> snapshot 预检读取实际 repomd/primary 并验证校验和及目标架构包；不以目录 HTTP 200 判可构建。及时归档源码、补丁、实际依赖闭包、buildconf、工具和元数据，在 WORKDIR 内建内容寻址存档，不依赖临时公共 URL。新 root 的离线复建通过之前，只称“已归档”，不称“离线可复现”。
>
> 依赖缺失时优先用校验通过的原锁定归档；不能恢复时停止该实验。批准更换 snapshot 后创建新实验 ID，重建全部对照及候选、重新采集，不把新 AFDO 配旧 BASE。profgen 工具升级可沿有限交付政策作输出回归；目标包性能实验不能仅凭工具回归跨依赖拼接。

PGOGEN 额外的 profile runtime 依赖可作为显式差异登记，不能借此放宽 PGO-use 与其对照的公共依赖。M1 已归档 108 个 RPM，可作为起点，不证明覆盖后续 PGO/GStreamer 新增依赖。

**验收：**same-NEVRA/different-SHA；BASE 后 URL 404；不完整归档；不同源码路径导致名字变化；宏相同而有效 ISA 不同；profile 宿主存在但 chroot 不可见；新 snapshot 必须使旧消费/测量节点失效。

### I2 — PGO 和 BOLT 没有各自正确的对照边

**位置：**W §3，42–48；S6 第 1 条；BOLT 路径第 2–4 条。

**问题：**BASE 带两项 profiling flags，PGO 却写成 platform flags + profile-use；这不是只差 profile。BOLT-IN 可以从 AFDO 派生，S6 却只列 BASE 对 BOLT；此时收益同时含 AFDO、重新链接/打包和 BOLT，不能归因于 BOLT。

**建议修改：**建立明确的比较图：

- M1：`BASE → AFDO`，公共构建锁相同。
- M2：优先让 `PGO → BASE` 使用同一公共 flags；PGOGEN 在同一公共配置上仅增加 instrumentation，保留正常预内联。若包必须使用另一组 flags，则增加 `PGO-BASE`，主比较为 `PGO-BASE → PGO`。
- M4：主比较始终是实际采样、未优化的 `BOLT-IN → BOLT`，两端同一父构建、依赖及部署策略。另报 `BASE → AFDO+BOLT` 时标成组合收益，不能叫纯 BOLT 收益。
- PLAT 继续可选，不强迫 M1 新增矩阵。

**验收：**每个候选只有已登记 control；BOLT 选 AFDO 父项却把 BASE 作为唯一对照时拒绝；比较报告同时保存 parent/control 的 ELF SHA，而不只保存变体名字。

### I3 — 部署校验不能代替“测量进程实际加载了这些库和插件”

**位置：**W S2、S3、S6；§6–7。

**问题：**S2 验证 push 文件，S3 保存 maps，但 S6 没有要求每个测量进程验证所有目标；`LD_LIBRARY_PATH` 也不控制 GStreamer 插件选择、registry 和 plugin scanner。已有脚本只观察一个 TARGET，不能原样推广为多 DSO 验收。

**依据：**`board/common.sh:133–159,172–190` 只读取单 TARGET 并确认其 maps；`prepare_board_bundle.py:51–66` 有 FFmpeg/lib*.rpm 特化。本地 GStreamer spec 的插件目录为 `%{_libdir}/gstreamer-1.0`（5 行），`libgstvideoconvertscale.so` 在 856 行，不能只设 `usr/lib` 就保证使用候选插件。

**建议修改：**包配置分开声明 `profile_targets`、`deployed_artifacts`、`must_load` 与固定依赖。S2/S6 对每个 workload PID/子进程保存并校验全部 must_load 的真实路径、SHA、映像身份；缺失或混入另一变体立即失败。包钩子设置并记录可执行程序、`LD_LIBRARY_PATH`、插件搜索路径、scanner、每变体独立 registry/cache，并在每变体预热前核对实际 factory→plugin 文件。不要禁止所有系统插件，而应把依赖于系统的插件及库锁定为相同公共输入。

所有 HOME/TMPDIR/XDG、perf buildid-dir、GST registry、profraw 及输出显式落入 `/opt/afdo_agent/`。身份校验适用于测量、PGO 训练和 BOLT，不限于 perf 采集。

**验收：**push 正确而进程加载系统库；libavcodec 正确但 libavutil 错；registry 仍指向旧插件；插件通过绝对路径 dlopen；子进程加载错误变体；缺少必需库但 workload 恰好退出 0。

### I4 — 正确性判据和计时边界未固定，散列相同不足以证明做完规定工作

**位置：**W S3、S6 第 3–5 条、§7。

**问题：**与 BASE 输出相同是有用的差分检查，但两端都提前 EOS、输出为空、协商了错误 caps 时也可能相同。示例没有明确 `sync=false`、输出格式/尺寸、帧数或 FIFO/hash 是否包含在测量中；实时同步可能把更快的解码固定到媒体时长，磁盘/散列瓶颈也会遮住优化效果。

**依据：**已用 `common.sh:161–170` 显式 I420、max-threads=1、sync=false；`measure.sh:32–50` 使用 FIFO+SHA，但以首个成功输出创建 expected digest，未验证帧数或非空。09 探测报告的 `identity eos-after=300` 是短探测负载，不能默认为完整 benchmark。

**建议修改：**每个输入在测量前锁定独立验证过的 BASE oracle：输入 SHA、流选择、帧范围、caps、线程数、预期帧数/字节数及 digest；训练输入也有自己的 oracle。每轮要求成功 EOS、非空、预期工作量和 digest 均匹配。输出格式允许数值容差的包，由 owner 预先给出逐元素比较和容差，不能看到差异后放宽。oracle 只保证规定工作负载的差分正确，不宣称完整媒体库正确性。

包 benchmark 明确计时边界、缓存政策和 sink：M1 可保留 FIFO+hash，但应称“固定管线端到端耗时”，记录校验进程 CPU/是否包含 drain，不称纯 decoder 时间；如果采用计时与 correctness 分离，必须证明执行的是同一配置与工作量。训练、测量、预试均固定 sink 行为，不使用时钟同步限速。

**验收：**空输出同 hash；少一帧；错误 caps；提前 EOS；hash 子进程失败；sink 阻塞；训练 oracle 与测试 oracle 混用；变体首次运行不能覆盖已锁定 oracle。

### I5 — “no new throttling”在已知 RPi4 上没有直接可用的判定来源

**位置：**W S0，77；S6，122；§13.4。

**问题：**S0 允许 throttle unknown，S6 却要求 no new throttling，没有定义 unknown、缺口、观测窗口和频率的含义。单看 governor、起始温度或两次 snapshot 不能发现中途降频；不能把安装散热当成正式测量资格已验证。

**依据：**`14_ffmpeg_frequency_diag.md:119–139` 记录 RPi4 无 vcgencmd/指定固件节点，欠压值全零时仍出现 600MHz 与 80.341°C。这些是旧镜像/会话事实；本轮没有验证当前板况。v1.8 `643–663` 已区分“现有遥测未观察到异常”与完整固件状态 unknown。旧 `common.sh:117–131,201–208` 不等价于这些新规则。

**建议修改：**S0 生成按板能力的 telemetry manifest，而不是两个板子共用未经验证的传感器假设。M1 至少固定并保存：每秒 policy、scaling/cpuinfo 频率、温度、可用欠压观测、单调时钟、前后窗口和缺口规则；优先复用 v1.8 已定义的异常/unknown 优先级及日志失败传播语义。完整固件状态读不到时单列 unknown，只可称“现有遥测未观察到异常”。若不采用 v1.8 全套校准，明确列出删减及残余混杂，不声称继承其全部验收。

必需观测缺失或异常不能按“没有发现新 throttling”通过。已知环境混杂的比较只作描述/inconclusive；原始结果不删除，执行 S1 的完整 block 规则。板上适配及监测扰动在各板首次正式测量前实测，不在本轮设计评审中假定通过。

**验收：**中途短暂降频后恢复；欠压零但频率异常；日志查询失败/回卷；观测窗口尾部缺失；RPi5 不同 policy/传感器；温度恰到门槛；missing 与异常并存；遥测进程自身导致明显耗时变化。

### I6 — package profile 缺少执行接口、构建单元和工作负载混合的必要字段

**位置：**W §6、§7、§8。

**问题：**目录约定和任意 shell 钩子不足以让 owner 独立交付。当前没有 schema version、钩子 argv/环境/输出 JSON、timeout、source/spec/宏、RPM→DSO→消费单元对应、ISA 区分、每目标门槛、训练权重和测试汇总规则。armv7l 一个列表不能区分 Thumb/A32。`spec_packages=[...]` 也无法表达同一源树按不同宏构建多个单元。

**依据：**GStreamer 本地 spec `17–58` 支持 `plugin=core/base/...`，默认 all；core/base 可以来自同一源树与 spec 的不同宏，也可作为 all 构建的子包。`137–155,526–568,856–875` 显示 base 库/插件产物。不能把“core、plugins-base”直接假定为两个独立源码仓库或无参数的 GBS 命令。

**建议修改：**v1 只增加必需的薄 schema，不做插件框架：

- `schema_version`、owner、源码/overlay 锁；`build_units[]` 含 spec、宏、arch、isa、产物选择器、消费 profile 的 staging/注入位置。
- target 含稳定 ID、所属 build unit、RPM/ELF/SONAME、must_load、每目标质量门槛；运行环境与可执行路径显式声明。
- workload 含 train/pilot/test 角色、输入 SHA/片段范围、重复次数、线程/亲和性、timeout、oracle、预期工作量、训练权重。
- hook 固定 argv 和 JSON 输出协议，例如 metric value/unit/direction、workload/correctness 状态、产物路径；禁止从任意 stdout 猜数值，非有限值拒绝。
- `period` 与 `freq` 互斥；多个训练输入默认按“相同固定工作量重复的原始计数和”合并，其他权重由 owner 预定并记录。P_ref 相同只统一单位，不自动平衡长短 workload。
- 输入按 SHA+片段检查 train/test 不重叠；测试输入不得用于参数择优，M4 调参另设 tuning 数据。登记前已看过的测试历史如实披露，不承诺从未接触过的 holdout。

**验收：**缺字段/未知枚举、Thumb/A32 混配、同文件异名跨 train/test、同文件重叠片段、缺目标子包、timeout、非 JSON/错误单位、不同训练重复次数未声明权重。M1 固定一个输入和一个耗时指标即可，保留将来扩展位置。

### I7 — “合并包内所有 DSO”没有命名空间或消费路由约束

**位置：**W S4，111；§7，209；PGO 路径。

**问题：**build-id 校验发生在生成阶段，合并后的 sample profile 并不带每个 DSO 的隔离命名空间。包内不同 DSO 的相同函数/context 名可能被静默相加，随后把总 profile 无区别给所有编译单元，未必是期望语义。固定 period_unit 不能解决这个问题。

**依据：**LLVM `llvm/tools/llvm-profdata/llvm-profdata.cpp:1638–1647` 按 `SampleContext` 调用 merge，键中没有这里的 DSO/build-id；`-funique-internal-linkage-names` 也不保证所有外部同名定义隔离。当前 FFmpeg 是否实际存在有害碰撞，本轮未读取正式 profile，**未核实**，不能说已发生。

**建议修改：**先按 `(build-lock, ISA, target DSO, event, weight, P_ref, workload policy)` 合并跨 RUN 产物；由 build unit 明确路由消费 profile。跨 DSO 合并须有同名/context 冲突检查及 owner 的同源合并依据；有异义冲突时拆分消费单元，不能静默相加。若 FFmpeg 构建暂时只能注入一份 profile，先验收全包合并前提，或在 M1 只优化一个已明确路由的目标，不伪称两个都已优化。

PGO 同样登记 PGOGEN 身份和文件清单，区分 setup/scanner、warm-up 与正式训练输出；只合并该 generation 的完整 profraw，不能 glob 整个目录的历史文件。保留 `%m/%p`、进程退出和 flush 记录；merge 成功不等于训练内容完整。

**验收：**两个 DSO 有同名异义函数；相同上下文跨 RUN 正常累加；不同 ISA/P_ref/生成身份混入；重复收据输入二次合并；PGO setup profraw 和异常退出的残缺文件不得进入训练集。

### I8 — S5 的 consumer coverage 不能按一个包级百分比直接实现

**位置：**W S5，115；§6，184；§13.2。

**问题：**两个选项是函数级、低于阈值时发警告，默认 0 表示不启用；“没有警告”不等于 profile 已被消费，更不等于 100% 包级覆盖。完全未找到 Samples 的函数可能不进入该诊断。当前 `min_profile_coverage_percent` 没有说明记录覆盖率还是样本覆盖率、按函数还是按包。

**依据：**`SampleProfileLoaderBaseUtil.cpp:26–34`；`SampleProfileLoaderBaseImpl.h:1100–1125` 逐函数计算并仅在低于阈值时诊断；`SampleProfile.cpp:2299–2322` 无 Samples 时直接返回。`Clang.cpp:6277–6282` 确认启用 sample-use 时驱动默认注入 Profi，v0.1 保留该默认可行。

**建议修改：**配置改为分别命名的 `record_coverage_warn_percent`、`sample_coverage_warn_percent`，并明确 `fail_on_coverage_warning` 的判定范围；不提供未经实现的包级百分比。保存实际 compiler argv、所有 stderr/退出码及 profiler 消费阶段；用小型代表 TU/预先指定目标函数的优化记录或 IR 证明 profile 参数被应用，另报“未找到 profile 的函数”，不可从无警告推导成功。M1 可以先只报告诊断，但若没有任何正面消费证据，不能把运行称作“已验证的 AFDO 消费构建”。

**验收：**漏传 profile；名字/路径错配导致零消费；低于阈值的函数；N=0；记录与样本两种百分比不同；compile 成功但没有正面消费证据。参数证明用合成 profile/TU，不用正式测试集来选阈值。

### I9 — BOLT 的预聚合契约、打包及参数选择还不足以执行

**位置：**W BOLT 路径，139–145；§10/M4。

**问题：**路径方向可行，但 `<address>/<count>` 未定义；S3 支持变频采样，count 若一律按样本数会与 period 加权语义不同。`E/S` 格式也不能替转换器执行身份验证。“re-attach symbol table”不保证重定位和地址来自同一个最终 ELF；“M4 trials 选择参数”没有隔离调参与正式测试。

**依据：**`bolt/lib/Profile/DataAggregator.cpp:195–198` 确认 --pa 不启动 perf；`1245–1258` 解析十六进制裸地址，`1337–1371` 读取整数计数并累计。该 S 路径没有替调用方核对 build-id。发布树 `IPPerfReader.cpp:252–260,394–423` 使用唯一可执行 PT_LOAD 的文件范围及 `VA=p_vaddr+dsoff-p_offset`。`bolt/README.md:12–25,120–124` 要求符号表并说明汇编/重定位限制。`BuildIDRewriter.cpp:96–103` 默认翻转 build-id 最后一位，不能把 BOLT 后 build-id 当作内容 SHA。

**建议修改：**M4 第一版只支持固定周期 `cycles -c P`，逐记录核对实际 event/period；每个合法目标 IP 贡献 1 个 basic sample，按 ELF VA 聚合后输出十六进制 `S VA count`、`E cycles`。明确这是采样热点，不是指令/边执行次数；不套用 profgen 的行级 max 聚合。频率模式留后续另定 period 加权规则。

转换器在写出前复用/等价实现逐映射身份、生命周期及 PT_LOAD 校验；保存目标最终 ELF SHA、build-id、输入 SHA、转换规则、丢弃/未知/LOST 汇总及前后计数守恒。冲突失败，缺身份默认不进入正式 BOLT 路径。pre-aggregated 和 fdata 的 sidecar 必须绑定同一 BOLT-IN SHA。

打包优先保留一个同时具备可执行字节、symtab、静态 relocations 的最终 BOLT-IN；不要以 debug-only ELF 或不明来源的 symtab 拼接替代。若重附元数据，独立证明地址、代码、relocations 均来自相同链接产物。验收 program headers、动态依赖、SONAME/导出版本、relocations、异常展开及实际加载；BOLT 后重新记录 SHA/build-id/debug 关联，禁止沿用旧 debug 身份。不支持的函数/重写比例如实报告，不把工具退出 0 当全库成功优化。

参数只在 tuning 输入上选择并锁定，再用测试集测一次预定矩阵。M4 先完成一个 AArch64 DSO 的 no-op/基本转换正确性，再启用 block/function reorder；可失败并报告不支持，不为满足 M4 而放宽身份或正确性。

**验收：**PIE/DSO 随机装载；多 PT_LOAD；p_memsz 超出 p_filesz；重映射/同路径换 ID；变 period；计数溢出/负数；同 ELF 不同优化输出不得仅凭相同 build-id 混用；缺 relocations/符号表；目标外样本；保留符号版与 debug-only 文件区分。本轮未构建 BOLT，Tizen 共享库端到端可行性仍为未核实，不阻塞 M1。

### I10 — 恢复与清理只挂在成功链末端，redo 也没有使下游失效

**位置：**W §4、S8、§9。

**问题：**fail-stop 发生在 S0/S3/S6 后可能永远到不了 S8；板子留下 root/governor/后台进程。只验证“最后阶段输出”也不能防止 package 配置、输入、源码或上游收据已经变化。`--redo S3` 归档 S3 后，旧 S4–S7 若仍被标为完成，会消费旧 profile 或旧报告。

**建议修改：**阶段收据记录全部直接依赖的 SHA（包含脚本、package profile、build-lock、输入、板会话及上游收据），形成小型 DAG。恢复时验证依赖链；redo 自动使全部后代失效，不能重用其完成标记。S0–S6 的板状态变更由 session/finally 清理负责，S8 是可重入的显式补偿命令；断连后记 cleanup_pending，下次重新确认设备身份和会话才恢复。保存原 governor/root 状态，不把固定 schedutil/off 当作所有会话的原状态。只停止自己的进程、只删除已核验拉回的确切目录。

`pull_verified_run.py:33–56` 已有拉回再校验再删除的良好基础，但 `134–138` 是先删除、后写最终收据；workflow 应先持久化“已拉回且验证”的收据，再做远端删除并记录结果，断电恢复不依赖远端原件尚存在。

**验收：**S3/S6 失败、SIGTERM、断连、收据写失败；删前/删后崩溃；redo S3 后 S5 不得仍 completed；package.toml 变化；数据文件内容变但文件名相同；板重启或设备别名指向另一台时不得自动恢复旧状态。

## 4. 一般问题

### G1 — “每个工具都有 build-id”与已交付工具事实不一致

**位置：**W §2.3、S0/S1。

**问题与依据：**`delivery/01_release.md:332–340` 明确发布 llvm-profgen 及其 debug 均无 build-id，使用 SHA 和 debuglink CRC 验证；不能使已交付工具因总原则字面要求而无法准入。

**建议修改：**区分工具与被采样目标：工具/脚本/数据以 SHA 为必需，工具 build-id 若有则记录；目标 runtime/debug 按已交付 IP 契约要求身份。对无 build-id 的发布工具记录 `none`，不得伪造；其 loader、libLLVM 等实际运行依赖也记录 SHA。不改 profgen 或发布决定。

**验收：**现有发布工具无 ID 但 SHA/依赖正确时通过；工具 SHA 错误失败；被采样目标缺 ID 仍按该目标正式策略处理。

### G2 — allow_unverified_identity 的配置与示例命令不闭合

**位置：**W S4，100–109；§6，183。

**问题：**配置允许 unverified，但命令没有条件添加 `--allow-missing-build-id`；工具会在 workflow 判断 JSON 前拒绝缺证据。反之，仅加该选项也不能放行 ID 冲突。

**依据：**交接报告 `197–203`、发布使用说明 §6.2；有限交付不改变该 CLI。

**建议修改：**M1 默认 false；显式 true 时才添加 `--allow-missing-build-id`，要求包配置说明缺证据原因，并在所有报告醒目标成 unverified。它只放行缺证据，不放行已知冲突；正式收益报告是否允许该模式必须有固定政策，建议仅供诊断。三个质量阈值保持可选、按包决定；LOST unknown 的处理另列策略，不把未失败解释为采样充分。

**验收：**缺 ID 且 false；缺 ID 且 true；已知冲突且 true；旧 ok JSON 配本次非零退出；质量门槛 absent/unknown 不得改写成 adequate。

### G3 — 把历史脚本当模块直接移入，会继承固定路径、旧并行度和包特化

**位置：**W §2.6、§8、§10。

**问题与依据：**`eval_build.py:20–22,45–48,75–77` 固定路径并用 nproc/2，不是最近 M1 的 -j2/6G 策略；`common.sh` 和 `prepare_board_bundle.py` 明确特化 FFmpeg/spike。设计说 evolved from 是合理的，但还缺一个复用边界。

**建议修改：**复用已验证的身份、拉回校验和命令语义；把路径、资源、包选择迁入显式配置，不直接调用历史执行器。M1 默认采用本次已实测成功的串行 -j2、6G/200% 资源档，host 门槛可显式配置但不得修改他人任务；verbose 参数不得进入 `_smp_mflags`。保持 debugedit 诊断原文，依据产物身份/DWARF 验收判定，不能看到 DWARF5 警告就自动改编译 flags。

CLI 暂只固定 M1 必需命令和收据；TOML→JSON 双格式 fallback、通用插件发现、任意指标、全自动 N、跨包并行调度可延期。M1 固定一个配置文件格式、一个耗时指标和显式 N 即可；M4/M5 模块留接口，不先实现。kernel profile 只保留边界说明，不提前设计 vmlinux/modules 采集字段。

**验收：**命令生成的资源/路径边界、只含 -j2 的 `_smp_mflags`、其他会话任务不被操作、旧 FFmpeg 分支不泄漏到核心。无需本轮运行构建验证。

## 6. 可行性、删减与实施顺序

M1 的目标构建可行性已有真实支持：M1 报告 §9 的 Thumb/A32 GBS 退出均为 0，分别 303.082/314.093 秒，每侧 23 个二进制 RPM；两库打包 runtime/debug 的 SHA-1 build-id 一致，DWARF 可读。不要再把旧 V=1 或 debugedit 诊断本身列为当前构建阻塞，也不要因此宣称 AFDO 消费、性能或 AArch64 构建已经验证。

建议保留 S0–S8、包配置、收据及逐阶段 CLI，不增加 Agent/HTTP 服务设计。按如下顺序收敛：

1. M1 先闭合一个 FFmpeg Thumb 目标链：依赖锁 → BASE/AFDO 消费证据 → 真实加载/正确性 → 固定测量计划 → 失败恢复。显式 max/none/none/none 原样保留，三个阈值政策由包配置决定，不重开默认值评估。
2. M2 再加入 RPi5、PGOGEN/PGO，验证 compiler-rt profile runtime、profraw flush/merge 与正确对照；不以小程序 PGO 成功代替包级验收。
3. M3 用具体 GStreamer profile 验证薄 schema 是否足够，而非先构建通用插件框架。
4. M4 独立验收 BOLT 转换及 ELF 重写；无 LBR 的收益可能小，正确且 inconclusive 也是有效里程碑结果。BOLT 的失败不能倒逼放宽 M1 的已交付工具契约。
5. M5 CLI 和失败语义稳定后再封装 SKILL.md。内核单列，未发现需要为本轮用户态 workflow 扩展内核范围的理由。

**最终结论：修改后可以实施。严重 1 项、重要 10 项、一般 3 项。**
